# Goal-directed execution

**Authority: approved M2 design.** This design replaces the superseded native-first proof-engine
approach. It changes the existing execution methodology and its gate/seal owners; it creates no
second execution path.

## Current checkpoint

The accepted implementation is byte-equal across its 13 candidate, public, installed Claude and
installed Codex mappings and is installed through the existing installer. The repository gate and
focused installed scheduler checks pass; the real installed scheduler accepts T1's eight normalized
writes. The implementation candidate was sealed and independently accepted. A fresh
normal-configuration native Codex read-only run returned `ACTIVATION PASS` for the approved
continuation and recovery behavior. Claude skills, hooks and personas are statically verified;
authenticated Claude inference is deferred. This final documentation tree is sealed and
independently accepted. Exact-tree seal and independent acceptance remain required conditions for
guarded conditional branch push, pull request and merge. Existing pinned consumer bindings are
unchanged; tag and deployment remain excluded, and the one-week review remains future.

## Design intent

The chief carries an approved milestone to closure by using the repository's existing scheduler,
task lanes, source owners, fresh judges, gate, seal, installer and publication guards. Product and
UX closure happen before implementation. Recovery changes the technical approach while preserving
the original cause and evidence.

## Existing path

1. The product steward closes requirements, context and one coherent milestone batch. A separate
   founder-approved UX journey supplies implementation authority where UX applies.
2. The chief derives the ready set from the approved plan, selects only file-disjoint work and
   delegates each logical task to its existing owner.
3. Ordinary work uses a Light dispatch. A Full card is required only when the task changes a
   durable interface or safety boundary.
4. The task's adjacent tests and area check run against its complete source/public change. Fresh
   read-only judges review the frozen delta through the existing eligible native route.
5. The chief integrates accepted work, drives causal recovery where needed, and repeats affected
   evidence only when its inputs changed.
6. Accepted maintained bytes are projected to their declared public paths and installed through
   the existing installer. The full local gate, seal and fresh acceptance bind the same unchanged
   candidate.
7. Existing guarded publication may act only under its matching conditional grant. Tags and
   deployment remain separate.

## Authority and persistence

The approved scope, frozen inputs, write boundaries, permissions and revocation state form the
working authority. A session or checkpoint does not expire it. The chief rechecks authority at
resume and before external action, and asks again only for a material scope or safety change, a
revocation, or an external action outside the grant.

The chief is the single scheduling owner. Builders do not approve their work. One fresh semantic
reviewer judges each logical task, with a relevant specialist only for a distinct boundary and a
security validator for a safety surface. Test judges report real command results.

## Task boundaries

Each task declares an exact normalized nonempty write set and nonempty `covers:` set. The scheduler
retains dependency, overlap, commit-scope, task-count and Full-lane schema checks. The arbitrary
limit that rejects a coherent task merely because it names more than five exact paths is removed;
broad globs are not an alternative. A task with many unrelated writes is still recut by judgment
and review.

The M2 implementation consists of two file-disjoint logical changes:

- **T1 core workflow:** closure, chief autonomy, compact dispatch/reporting, persistent authority,
  causal recovery and the retained scheduler invariants.
- **T2 gate and seal integrity:** complete verdict propagation and post-gate candidate/evidence
  freshness.

Mechanical maintained-to-public projection keeps the originating task identity and review. It does
not create another implementation task, card or scheduler.

## Causal recovery

The chief preserves one cause and finding lineage across renamed attempts, fixtures and diagnostics.
A and B test revised causal hypotheses. Stronger available model or effort may be used as soon as
evidence justifies it. Before C, a targeted expert council must produce a technical replan and a
fresh independent reviewer must pass it. C failure ends automatic recovery and returns the decision
packet to the founder; there is no fourth approach.

At the existing recovery or handoff boundary, a proposed control must answer:

1. Which approved criterion requires it?
2. Why is the existing owner insufficient?
3. Which delivery outcome does it unblock?

Those questions are part of the existing dispatch and recovery conversation. They add no form,
counter, checker, ledger or routine council.

## Gate, seal and freshness

The existing declared-gate launcher returns nonzero whenever any terminal verdict is nonpass,
including integrity failure after the child command. The seal owner records success only after the
gate completes and the candidate, source, frozen inputs, command, runtime and evidence remain the
bound values. Verification refuses stale or mismatched receipts. The seal binds repository root,
HEAD, tree, milestone document, command and clean tracked source under the local operator trust
model. It does not attest the dependency or service environment and does not defend against a
hostile concurrent writer. Mechanical seal validity does not replace semantic acceptance.

## Projection, installation and closure

Maintained source is the implementation origin. Accepted bytes were projected only to the exact
public paths declared by T1 and T2, verified byte-equal, and installed through the existing
installer and sync owners. M2 adds no consumer binding, activation lock or installation protocol.

The final full local gate runs once against the unchanged candidate. A valid seal and fresh
independent acceptance then bind that same candidate. Conditional push, pull request and merge use
existing guarded tooling only while the approved publication tuple and authority remain valid.

## Explicit exclusions

No new runner, adapter, service, execution mode, schema, ledger, model default, permission profile,
activation lock, publication implementation, paid or hosted continuation, consumer binding, tag or
deployment is part of M2. The one-week business-value review reads existing evidence and introduces
no pilot or measurement system.
